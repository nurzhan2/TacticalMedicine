# LAUNCH_FIX — why the V1 APK "did not open" on the Quest, and what w0 changed

Stage w0-launchfix, 14.10.2026. No headset was connected during the night, so everything below comes from the
project: settings, the generated Gradle project / merged manifest of the V1 build, the APK itself, Meta's own
project-setup validator, and new editor/PlayMode tests. `tools/quest_check.ps1` does the on-device check as soon
as a headset is plugged in.

So there was **no single hard blocker** in the manifest. The problems found are below; each one could produce an
"it does not open / nothing happens" report on its own.

## 2. Problems found and fixed

1. **Long black screen at start (most likely the "did not open").** The APK started directly in `Main.unity`
   (3.7 MB scene, whole battlefield + casualty + audio). Loading it took **16 s** in the editor; on the headset the
   player sees the Unity splash and then black until everything has loaded and run Awake/Start.
   **Fix:** a new tiny first scene `Assets/Scenes/Boot.unity` (generated by `SceneBuilders/BootSceneBuilder.cs`):
   OVRCameraRig + black background + "БАУЫР / Field Medic VR · TCCC / Загрузка / Жүктелуде… NN%" panel that
   follows the head. `UI/BootLoader.cs` loads Main with `LoadSceneAsync` and logs `[FMVR] boot: Main loaded in X s`.
   Build scenes are now `[Boot, Main]` (`MainSceneBuilder.SetBuildScenes`). Scenario restarts still reload the
   active scene (Main), so Boot is shown only once.

2. **Controllers did nothing in the first scene on the headset.** `HandRig` chose its input source once, in
   `Awake`, from `XRSettings.isDeviceActive`. XR Management starts the display subsystem only *after* the first
   scene has loaded, so on the Quest that flag was still false: both hands fell back to the desktop (mouse/keyboard)
   simulator and stayed there. The menu could not be used until a scene reload, which never came.
   **Fix:** `DesktopSimulator.XRActive` is always true in the Android player (`#if UNITY_ANDROID && !UNITY_EDITOR`);
   `DesktopSimulator` disables itself on the headset, so it can never move the tracking space or lock the cursor;
   `HandRig` switches from desktop to headset input as soon as XR becomes active (also fixes Quest Link in the
   editor). Tests: `InputLayerTests.HandRig_Switches_To_Headset_When_XR_Starts_After_Awake`,
   `LaunchSmokeTests.MainScene_Starts_On_Headset_Path_Without_Errors` (Main on the headset code path: no error
   logs, hands in OVR mode, tracking space still at floor level).

3. **Unused Horizon OS supplement dependency.** The Meta Platform SDK (pulled in by `com.meta.xr.sdk.all`) injects
   `<horizonos:uses-horizonos-supplement name="horizonos-supplement-hzplatformclientcore" minSupplementVersion="1">`
   into every build (`ModifyAndroidManifest.cs`). The trainer never calls the Platform SDK (no app ID), but the
   entry makes the APK depend on an OS supplement library that a headset may not have.
   **Fix:** `QuestManifestCleanup` strips it (the `uses-horizonos-sdk` min/target entry stays).

4. **Only Quest 3 / 3S were allowed.** `com.oculus.supportedDevices` was `quest3|quest3s`; on a Quest 2 or Pro the
   OS refuses to start the app ("not supported on this device").
   **Fix:** `quest2|questpro|quest3|quest3s` in `Plugins/Android/AndroidManifest.xml`, OVRProjectConfig target
   devices, and forced by `QuestManifestCleanup` in the generated manifests. (Quest 3/3S remain the target; Quest 2
   will run with lower frame rate.)

5. **Risky, unused OpenXR features were on.** Unity *Space Warp* (needs motion-vector passes we do not render) and
   *Meta XR Subsampled Layout* (subsampled Vulkan eye buffers combined with our dynamic resolution) were enabled.
   **Fix:** switched off by `QuestLaunchSetup`; foveated rendering still works via Meta XR Foveation.

## 3. Guard rails added (so it does not regress)

- `Editor/QuestLaunchSetup.cs` — runs at the start of every `BuildTools.BuildAndroid` and enforces: IL2CPP, ARM64,
  minSdk 32, GameActivity, Vulkan first, no Android TV, build scenes `[Boot, Main]`, required OpenXR features on,
  risky ones off, Meta Quest Support targets incl. Quest 3/3S, OVR target devices Quest 2/Pro/3/3S. Logs every
  change as `[FMVR] QuestLaunchSetup: ...`.
- `Editor/QuestManifestAudit.cs` — after every build it reads the **final merged manifest** and fails the build
  (exit code 2) if: no MAIN+LAUNCHER activity, no `com.oculus.intent.category.VR`, activity not exported, minSdk
  < 32, supportedDevices without quest3/quest3s, any `uses-feature` required=true except head tracking / Vulkan,
  any required `uses-library` / `uses-native-library`, a `uses-horizonos-supplement`, or a prompting permission.
  Report: `logs/manifest_check.txt`, copy of the manifest: `logs/merged_manifest.xml`. EditMode tests cover each rule.
- `BuildTools.BuildAndroid` copies the APK to the Desktop after a successful, audited build.
- `tools/quest_check.ps1` — on-device check (see below).

## 4. How to install and check on the headset

1. Headset: developer mode on (Meta Horizon app → device → Developer mode), USB-C cable to the PC, put the headset
   on and accept "Allow USB debugging".
2. `powershell -ExecutionPolicy Bypass -File tools\quest_check.ps1` — installs `Builds\FieldMedicVR.apk`
   (`adb install -r -g`), starts it, waits 40 s, saves `logs\quest_<time>.txt` (Unity / AndroidRuntime / OpenXR /
   crash lines) and `logs\quest_<time>.png` (headset screenshot), prints **PASS** / **FAIL** / **NO DEVICE**.
   If the old V1 copy was signed with another key the script uninstalls it and installs again.
3. In the headset the app is in **Library → filter "Unknown sources"** (sideloaded apps are not in the main list).
